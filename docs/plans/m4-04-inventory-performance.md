# M4-04 库存查询性能基准

2026-11-24 本机样例实测。余额、流水和入库统计共 60 次查询全部返回预期结果。入库统计客户端 p95 为 2.37 秒，超出 2 秒参考值。PRD 的指标采用服务端计时，本轮未采集服务端独立计时。

| 查询 | 次数 | 客户端 p95 | 最长 |
| --- | ---: | ---: | ---: |
| 单库房、单型号余额 | 20 | 36.2 ms | 37.9 ms |
| 指定日期的流水明细 | 20 | 56.3 ms | 56.8 ms |
| 指定日期的入库统计 | 20 | 2371.5 ms | 2372.7 ms |

**数据与核验**　通过正式建账入口生成 1 条期初流水，批量构造同一库房、同一型号的 9,999 条虚构入库单与对应流水，分布在 100 天，每笔 1 台。对账接口返回一致。所有余额响应的在库、预留、可售和版本分别为 10,009、3、10,006 和 10,000。五个会话共查前 20 个不同日期，每日返回 100 条流水，逐条核对版本顺序和数量变动。入库统计逐日核对总量、单据数与发生日期。

**运行口径**　本机 Windows、专用 PostgreSQL 测试库、独立单进程 Uvicorn。5 个登录会话每轮同步发起同类请求，每类 4 轮。计时从客户端发出请求到收到完整 HTTP 响应，排除登录、构数及客户端 JSON 校验。p95 取每类 20 个样本排序后的第 19 项。模型和 OCR 均调用 0 次，外部调用费用为 0。本轮覆盖有日期筛选的查询，全历史明细、大范围统计、混合写入和正式环境仍待测。

**首轮未达项分析**　现有入库统计先读取该库存对象所有入库与更正记录，在应用层构建单据后才按日期过滤。建议针对本次单日范围量测 SQL、ORM 加载及应用层处理时间，验证将日期筛选前移时仍保留更正单关联和 T0 覆盖语义，再以同一脚本复测。正式环境验收应增加服务端计时。

**复测**　在项目根目录将 M1_TEST_CONFIG 指向专用测试配置，运行 `python -m pytest -q -s tests/acceptance/bench_inventory_queries.py`。测试会重置本机专用测试库，应独占运行。本次 pytest 结果为 `1 passed in 15.31s`。

## 2026-11-25 同口径复验

日期条件已移到 SQL 外连接，先按原单的上海自然日筛选入库单，再关联更正。仍保留日期范围以外登记的更正及无单据对象的 T0 覆盖。用同一数据规模、同一并发和相同的业务断言复测。服务端时间从测试 ASGI 应用接收请求到发出响应头，客户端时间包括读取响应体。计时组件仅在基准进程加载。

| 查询 | 次数 | 服务端 p95 | 客户端 p95 |
| --- | ---: | ---: | ---: |
| 余额 | 20 | 20.4 ms | 26.7 ms |
| 单日流水 | 20 | 36.4 ms | 39.1 ms |
| 单日入库统计 | 20 | 63.1 ms | 65.3 ms |
| 档案完整电话 | 100 | 19.7 ms | 26.6 ms |
| 档案部分地址 | 100 | 20.5 ms | 22.7 ms |

本机两个专用数据集分别运行，库存 60 次、档案 200 次查询均核对结果。各项服务端 p95 均在 2 秒建议值之内。更正密集的长期数据及正式试用环境仍待复测。库存报表、案例审核及两项基准合计 9 项通过（21.53 秒）。
