# 开发规范

用于代码、测试和交付任务。业务规则以[PRD](../prd/store-service-agent-prd-v1.0.md)为准，实现边界见[架构](../architecture/store-service-agent-architecture-v1.0.md)，任务顺序见[开发计划](../plans/development-plan-v1.0.md)。

## 动手前

- 先读取涉及的代码和对应文档，明确当前能力、预期行为及完成条件；能由文件回答的问题先查文件。
- 说明影响范围或业务行为的重要假设。存在不同解释时指出差异，影响业务规则或范围的分歧先澄清。
- 多步骤任务给出简短计划，每步带验证方式；不要只写“让它正常运行”。

## 实现与改动范围

- 优先采用简单方案，不增加未要求的功能、依赖、抽象、配置或不可能场景的错误处理。
- 沿用现有代码风格，不顺手重构、改格式或清理无关死代码。每一处修改都应能追溯到当前任务。
- 保留已有修改和暂存内容，不覆盖或回退他人的工作；只移除本次改动造成的孤立导入、变量和函数。
- 后端优先沿用Python/FastAPI；其他技术选择按已有代码与实际需求决定，不提前堆叠组件。
- 页面任务另读[设计规范](../design/design-resources.md)，不用前端模拟计算或成功文案代替正式业务结果。

## 验证与交付

- 代码修改执行与风险相称的检查；业务规则与修复使用能证明行为的测试，先明确失败输入和预期结果。
- 库存并发、事务与幂等使用真实PostgreSQL验证；不以UI样例或另一数据库的通过结果替代。
- 纯文档修改检查内容、链接、路径和格式即可；不为低风险可逆修改堆叠无意义测试。
- 报告实际执行的命令、结果及未覆盖项，不虚报测试、业务效果、性能或费用。
- 任务状态随证据更新。代码完成、测试通过、门店试用和生产上线分别表述。

## 文档协作

- 需求、技术设计、实施计划分别维护各自事实，不复制同一套规则；按[文档入口](../README.md)定位维护源。
- 页面变更同步设计规范AI/HTML两版和核对记录；概念图、可交互样板、生产能力明确区分。
- 删除或移动文档前检查引用，先迁移独有的有效信息，再删除重复内容并修复链接。
- 保留仍作为依据的原素材和核对证据；过期结论标注适用阶段，不能冒充最新验证。
